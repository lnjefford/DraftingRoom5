# DR5-062 progression application handoff

The repository now applies a progression choice and its durable receipt in one current-document write. This is the application layer for DR5-063; no workout sheet is wired in this task.

- Read `document.progressionOffer(sessionId, exerciseId)` after a persisted final set. A missing offer means there is no eligible decision. The offer captures both session-event and live-routine revisions and includes complete resulting exercises and ordered additions.
- Submit `offer.request(choice)` through `AppRepository.applyProgression` with the current session lease. Only the repository's recalculated option is accepted; callers cannot supply arbitrary replacement prescriptions. Failure leaves the committed document unchanged and the same request can be retried.
- Weight-only, duration-only, and heavier/shorter are explicit alternatives. There is no increase-both choice. Increments clamp to configured bounds; unavailable/no-change alternatives disappear. Without explicit bounds, weight stays finite and duration remains between 1 and `Int.MAX_VALUE`. Decimal pounds increments avoid cumulative binary addition error.
- Numeric changes preserve free-text target, name, notes, sets, artwork, progression configuration, and unselected measurements. A changed structured duration also becomes the timer duration. DR5-063 must show the resulting structured pounds/seconds, rather than infer or parse them from target text.
- A custom step replaces the source prescription, preserves its ID, consumes precisely its first step, and inserts the configured exercise objects immediately after it in configured order. The last step clears custom progression. Existing additions are ordinary independent exercises; later source changes never revisit them. Nested custom additions retain their own future steps.
- Receipts are keyed by session ID and exercise ID, survive recreation/finish/restart, and remain after Undo. Retrying returns the saved receipt without a write or revision increment, including when `undone` is true. The UI must not interpret every successful retry as a newly applied transition or replay feedback. A handled completion has no further offer in that workout.
- The live source must still equal the completed snapshot source. An intervening progression of that source, even followed by Undo, makes older snapshots ineligible. Other exercises in the same workout can progress using a refreshed live-routine revision. Incomplete work and stale session/routine revisions cannot advance.
- `undoProgression(lease, sessionId, exerciseId)` restores only the prior source and removes only that receipt's additions. Any subsequent routine mutation expires immediate Undo; session and preference writes do not. Undo itself advances the routine revision once and is idempotent. A later workout can advance the restored source again.
- Active and completed snapshots never change. Restart adopts the current routine with fresh session identity and zero counts. Old accepted-session IDs cannot be reused. Restore preserves receipts and revokes command leases; plan reset clears receipts along with sessions/history.
- The strict current schema requires `progressionReceipts`, including when empty. There is no development-data migration. Receipt identities, choices, and revisions are validated; the existing document size limit and atomic storage boundary still apply.
