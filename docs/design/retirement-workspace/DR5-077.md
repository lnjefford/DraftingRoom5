# DR5-077 — Retirement sync, lifecycle, privacy, and recovery hardening

## Delivered hardening

Linked-account and automatic-property refresh now share a process-wide per-source operation gate. A foreground retry and a WorkManager run for the same local item cannot issue overlapping provider calls; unrelated items remain independent. SQLite generation/revision compare-and-set and append-only ledger transactions remain the durable publication boundary across process restart. Provider operation receipts keep account batches idempotent, Epic confirmation is generation-bound and digest-idempotent, and Forecast publishes only a complete request whose repository generation and plan revision are still current. This prevents duplicate import/sync publication and mixed-generation Overview, Assets, and Forecast output.

Periodic work is unique per opaque item/property UUID and uses a versioned `UPDATE` policy, connected-network plus battery-not-low constraints, exponential 30-minute transient backoff, persisted provider retry windows, first-unlock gating, and three bounded retries for offline/unavailable/conflict outcomes. Authentication, unsupported/malformed data and cancellation wait for foreground action instead of looping. Account one-day and property seven-day intervals are Android scheduling requests, not delivery promises; Doze, battery policy, reboot/first unlock, connectivity and provider limits can delay or skip execution.

Offline/provider/workbook failures preserve accepted balances, holdings, property valuations, Epic data and their accepted timestamps. Failure metadata remains scoped to the affected item. Cancelled or superseded property work no longer reports success or writes an error. Provider and workbook commits remain atomic and recoverable after injected SQLite failures and repository recreation. Route restoration uses validated primitive route identities/generations; bounded non-secret Retirement forms use saveable state, while credentials, SDK tokens, workbook streams/URIs, provider responses, jobs and busy flags deliberately require secure re-entry, pending-item resume or file reselection after recreation.

Privacy checks retain the Fitness-only backup/device-transfer allowlist and no-backup Retirement database/vault. Work input carries only opaque UUIDs. Production Retirement source has no ad-hoc logging or stack-trace printing. The full Retirement/provider window remains `FLAG_SECURE`; secret fields disable save/autofill/content capture and are wiped where practical. README and TechnicalDesign now document the feature, provider topology, privacy/backup boundary, lifecycle/recovery rules, approximate background timing, external-provider limits and forecast disclaimer.
