# DR5-070 — Phone-only linked accounts

Implementation task: `01a0bc7b-6121-73b2-84b9-6a5b5318a5f9`. Push: **NO**. The v0.26.1 version defaults and accumulated DR5-067–069 work are preserved.

## Implemented boundaries

`retirement/provider/` owns the shared `ProviderCredentialVault`, Android Keystore adapter, restricted transport, `PlaidNativeProvider`, reconciliation, private connect/reconnect Activity and daily WorkManager entry point. `RetirementRepository` remains the sole financial transaction owner. Assets exposes functional connection/manual/attention actions; final grouped account-list/detail styling remains DR5-071. There is no companion, backend or Data sources destination.

The provider calls `/link/token/create`, `/item/public_token/exchange`, `/accounts/get`, `/investments/holdings/get` and `/item/remove` directly. Only fixed Plaid HTTPS origins and enum-selected paths are allowed. Redirects, URL credentials, body logging and HTTP caching are absent. Response size and JSON structure are bounded. Numeric JSON lexemes are retained as decimal text before Android JSON decoding, then normalized with BigDecimal HALF_UP to integer cents. Non-USD, missing required balances, malformed holdings and inconsistent item/account identities fail closed.

The SDK dependency is pinned to **Plaid Android 5.5.5**, which supports the repository's Kotlin 2.0 toolchain. The 6.2.2 POM requires Kotlin 2.3.10 and newer AndroidX versions; this item does not upgrade the entire application toolchain. The 5.5.5 versioned sample verifies `FastOpenPlaidLink`, `Plaid.create` and `LinkTokenConfiguration`. SDK logging uses its most restrictive ASSERT level; the application installs no event logger and never logs SDK success/exit objects or raw exceptions.

Private credential setup, replacement, removal and explicit lost-key reset live inside Connect/reconnect. Device credential authentication precedes access to these actions, and provisioning requires a configured device lock. Native password fields disable autofill, content capture, saved state and personalized keyboard learning. Our task window and provider Activity windows use FLAG_SECURE. API credentials are never passed in Intents, navigation, work input/output or application saved state. Only local opaque item IDs reach background work. Link/public tokens cross the SDK handoff transiently and are never copied into application persistence.

The vault wraps records with AES-256-GCM, a new 96-bit IV, 128-bit tag and AAD binding schema/provider/environment/local ID/revision. Android Keystore owns the key, tries StrongBox before platform fallback, and reports actual protection rather than assuming hardware. AtomicFile stores envelopes only at `noBackupFilesDir/retirement-credentials/vault.json`. Key use is permitted after first unlock, including subsequent screen lock, so background refresh does not prompt. Missing/unavailable keys never cause plaintext fallback. Mutable request/plaintext buffers are wiped; managed String copies cannot be guaranteed erased.

Exchange consumes an in-memory, expiring attempt once. Returned tokens are encrypted as pending items before review. A recreated task resumes pending review by opaque handle, never by replaying a public token. Expired pending records attempt revocation and are removed locally. A financial commit precedes clearing the pending flag, so interruption between the two durable stores recovers the committed accounts rather than losing their token. Removal retains accepted history and separately reports whether provider revocation was confirmed. Authenticated reset explicitly clears all provider credentials, including the future RentCast key, marks connections disconnected, and preserves financial records; users can explicitly match disconnected records during a new review.

Accounts require explicit selection, classification confirmation, owner and inclusion. Unknown subtypes never receive an accepted classification automatically. Account masks and names never identify an existing account. Exact provider identity prevents duplicates; converting a manual or disconnected account requires an explicit user-selected match. Active linked accounts cannot be taken over by another item. Sync preserves accepted local names/classifications and never writes manual balances to connected accounts.

Each fetch reserves a local item revision. Vault/profile revisions and database generation guard publication, preventing older fetches, reconnect results or rotated credentials from overwriting newer state. A complete item batch publishes accounts, snapshots, holdings and successful freshness in one SQLite transaction. Identical same-day values and unchanged holdings add no snapshots. Changed same-day values append history. Missing/partial responses never delete accounts. Failed refreshes preserve last-good values and attach safe status/errors to their affected item. Account attention is projected through the account's item identity. Reconnect uses update mode for that item only.

The clean version-1 Retirement document also persists accepted provider operation receipts. Replaying an accepted operation after later sync or repository recreation returns its accepted state without another write. There is no development-schema migration or change to Fitness persistence. The encoder enforces the same 4 MiB bound as the decoder, so growth cannot commit an unreadable document.

WorkManager uses unique item work, connected-network and battery-not-low constraints, approximately daily eligibility, exponential backoff and bounded transient retries. Authentication/invalid data stop retry loops. Provider Retry-After windows are respected. A stopped worker cannot publish a fetched batch. Android scheduling remains inexact.

## Verification and outstanding release gates

Sanitized JVM fixtures exercise provider success/cancellation/ambiguous exchange, pending recovery, duplicate masks, idempotency, same-day changes, classification preservation, explicit manual matching, scoped reconnect, stale tokens, offline behavior, unsupported holdings, atomic failure, worker cancellation, rate limits, credential rotation, lost-key reset, AES-GCM tampering/IV uniqueness, transport restrictions and redaction. They use fictional strings only and never open personal financial sources.

`RetirementProviderNativeAudit` uses an isolated no-backup directory and temporary key alias. It tests real Android Keystore encryption/recreation/tamper rejection and real SQLite failure after the first appended snapshot, rollback, append-only triggers and recreation. It does not use a live provider account.

The API 35 emulator audit **passed**: Android Keystore AES-GCM, IV uniqueness, plaintext canary exclusion from ciphertext, vault recreation and authenticated metadata tamper rejection; actual protection reported **Software Keystore**. The real SQLite test also passed rollback after the first linked snapshot, atomic classification/value/freshness publication, append-only triggers and database recreation. Initial attempts stopped at the device-unlock prerequisite; configuring the synthetic lock after boot resolved that setup issue. The temporary key and isolated database were cleaned up by the harness. The synthetic PIN was removed and the prior disabled-lock setting restored afterward. This is not evidence of hardware-backed storage on a physical phone.

The existing Python parity gate passes **103 reference assertions and 14 contract tests**. The final Android gate passed **332 unit tests**, **zero lint errors** (51 warnings), and both debug/application and instrumentation APK assembly. The accumulated screenshot gate passed **311 comparisons**, with no failures, errors or skips. Whitespace checks passed. Four synthetic vault-test canaries were absent from every decompressed application APK entry; this narrowly verifies test-fixture exclusion, not SDK runtime behavior.

Local cache/daemon contention and a duplicate build process delayed validation; the original final stable-source build completed successfully. No ACL restrictions were removed.
