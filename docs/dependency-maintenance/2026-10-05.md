# Dependency maintenance — 2026-10-05

This is the audit for the coordinated v0.29.21 maintenance release. The working tree started clean at v0.29.20; `origin/main` had the same commit after fetch, so no fast-forward was needed.

## Queue and security decision

The only open Dependabot change was [#23](https://github.com/lnjefford/DraftingRoom5/pull/23), with one successful Android commit-build check and no failing checks. It updates `com.google.guava:guava` from 33.7.1-android to 33.7.2-android and the Commons Lang minimum from 3.20.0 to 3.21.0. Both updates are accepted. Guava takes priority because [GHSA-xxph-c9ww-hj94](https://github.com/google/guava/security/advisories/GHSA-xxph-c9ww-hj94) affects all editions through 33.7.1 and names 33.7.2 as patched. The flaw permits oversized allocations when native Java deserialization receives a crafted collection stream; the app has no direct `ObjectInputStream` use, but the affected library is on its classpath. Commons Lang 3.21.0 is a [Java 8-compatible maintenance release](https://commons.apache.org/proper/commons-lang/changes.html).

The pre-change GitHub dependency graph included Guava 33.7.1-android in app dependencies and 33.4.0-jre through AGP, lint, bundletool, and related build tooling. The app constraint now selects 33.7.2-android; a separate buildscript minimum requests 33.7.2-jre without changing the Android runtime edition. The first main-push graph still contained 33.4.0-jre. A complete configuration trace isolated it to AGP's `androidLintTool` and `_internal-screenshot-validation-junit-engine` configurations in both modules. A 33.7.2-jre minimum constraint now applies to those two configurations. The second local trace confirmed every app runtime configuration resolves 33.7.2-android and both affected tooling configurations in each module resolve 33.7.2-jre. These are minimum constraints, not permanent exact pins. The graph also contained earlier patched Bouncy Castle, jose4j, JDOM, Commons Lang, and HttpClient floors. Dependabot reported no open repository alerts before this change, though the graph contained vulnerable Guava versions; zero alerts alone was not treated as a clean security audit.

The repository's Dependabot configuration has no ignore rules. Its `dependencies` label was missing and caused a bot warning on #23; the label was created and applied. No intentionally deferred PR or duplicate exists.

## Validation and delivery

The first `./tools/verify.ps1 -Tier Release` run passed 540 unit tests (534 phone, six Wear), lint, and both debug APK builds. Six of 530 phone screenshot comparisons failed solely because the footer still referenced version 0.29.20 and October 4. All six diff images were inspected, along with representative full reference/rendered pairs at compact and large-text sizes. The affected images contained no changed controls, layout, or clipping. Exactly those six phone references were updated; all 80 Wear screenshots and the other 524 phone screenshots were left alone. The second complete Release run passed in 709.4 seconds: 540 unit tests, lint, both debug APKs, all 530 phone screenshots, and all 80 Wear screenshots. No tests were skipped or failed in the final run. `git diff --check` passed.

The first full rerun with the added tooling constraints passed tests, lint, and APK assembly, then its screenshot executor crashed with native `std::bad_alloc` under the Windows two-worker setting before reporting comparisons. `tools/verify.ps1` now recognizes this native heap signature for its existing one-time, single-worker recovery path. The next run completed 530 phone and 80 Wear screenshot comparisons with zero failures, but Gradle could not store the screenshot cache entry because the isolated build drive had only 0.5 GB free. To address that confirmed disk-space failure, 3,473 old hash-named entries dated before October 2 were removed from the isolated Gradle **build cache** (12.76 GB), without running `clean` or touching source, signing, or reference images. The final `./tools/verify.ps1 -Tier Release` passed in 42.3 seconds after Gradle accepted the already-completed screenshot outputs as up to date; the XML reports show 530 phone and 80 Wear comparisons, zero failures and errors. Tests, lint, and debug APKs also passed. The final submitted dependency graph, GitHub CI, tag workflow, and publication results are recorded in the automation run summary after completion. The release tag is held until the main-push dependency submission has refreshed the graph and CI has passed.
